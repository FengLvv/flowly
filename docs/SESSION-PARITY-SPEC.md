# Session controls and native Paseo parity

## Decision and boundary

User-approved 2026-11-16: extend the existing server-only local daemon adapter for session model and provider-feature changes. This supersedes SESSION-UX-SPEC §1's prohibition on a new internal connection **only for these card-scoped operations**. Never create another client connection, import private host UI, change the host, or replace sessions to change a model. SDK/type versions and manifest remain pinned.

The public SDK (0.15.0 at implementation, upgraded to 0.16.0 during the 2026-11-17 upstream integration) exposes model discovery and live feature state but no resource-handle model/feature setters or embeddable native agent pane. The daemon client's `setAgentModel` and `setAgentFeature` remain the compatibility bridge; remove it when the supplied public resource SDK exposes equivalent operations. All other operations retain their existing SDK/CLI routes. No promise of pixel or host-plugin parity is made.

## Mutation and UI contract

- Extend `sessions.configure` with `modelId?: string` and `feature?: {id:string,value:boolean|string}`. Each new model/feature mutation is a single operation; reject mixed bundles before any side effect. The daemon rechecks the current non-archived task, project and session workspace before mutation. Validate models against fresh selectable provider discovery (including aliases for current-state matching), and features against the refreshed session's exact toggle/select shape. Unknown ids, wrong types and unavailable options fail without opening a connection. Serialize mutations per session and reject overlapping requests rather than replay them later.
- Open a short-lived authenticated local connection only after validation, require the relevant method, forward provider errors and always close it in `finally`. Log unexpected daemon failures with a fixed `logFailure` label and log-only context. Never expose credentials. No fallback to creating/reloading a session, clearing history or changing permissions.
- Composer menus are scrollable and height-bounded on desktop and compact layouts. Feature selection opens its advertised options; toggles display translated On/Off. Disable all configuration choices while an operation is pending or the task/session is not writable. A synchronous shared session lock blocks duplicate presses and overlap with send/answer/archive. Do not mark selection optimistically: the streamed/refetched session is authoritative. On success or failure refetch, including when the provider partly applied a change before rejecting; show error and allow retry. A late operation completion must not alter another selected session or a closed view.
- Feature controls remain independent on desktop and compact layouts. Feature selects anchor their floating menus to the right edge of their own trigger on desktop so later toolbar controls do not push the menu past the pane; compact menus remain inline. Opening model, reasoning, permission, a feature menu or Subagents closes the previous menu. Controls expose expanded state where applicable and toggles have a checked accessibility state. This is the user's 2026-11-16 follow-up to match native conversation controls.
- Provider feature icons reflect the effective host value with the menu closed or open. An enabled toggle or a non-default select choice uses the host's highlight family for Speed/Fast (yellow), Plan (blue), or Auto-accept (green). Other feature icons retain the neutral theme color. A missing or obsolete select value resolves to the provider's advertised default when present. Use that same choice for the trigger label, menu check mark, and redundant-write check. Keep select triggers as expandable buttons and toggles as checked switches. The keys for the three highlight families affect presentation only. Use the installed host swatches on dark surfaces and darker shades in the same families on light surfaces for contrast.
- The user's later native-composer screenshot supersedes the earlier interpretation of "rightmost": controls form one continuous flow inside the input border, in order Add (where image attachment is supported), model, reasoning, permissions, Speed, Plan. Feature icons follow permissions with normal spacing; no flexible spacer, right-pinned group or separate control row outside the input border. Keep provider feature order and wrap naturally on narrow panes. Send/Stop stays at the opposite end of the same footer, inside the border.
- Match the supplied native visual reference for supported controls: 32pt controls, readable labels, provider mark for Codex/OpenAI, Brain reasoning icon, ShieldOff for Full access (otherwise the current permission mode's advertised icon), then the provider's feature icons. Remove redundant dropdown chevrons from this compact toolbar; keep expanded/checked accessibility state. Render known reasoning levels and Full access with human-readable labels. The text area starts at 48pt and retains its existing bounded growth, native text ownership, drafts, keyboard and message delivery behavior. Use a theme surface/border and rounded composer frame; do not copy placeholder claims about unsupported @files/commands or add nonfunctional voice controls.
- Keep the native-session shortcut. No global polling, new dependency, persistence schema, version bump or telemetry field. This exposes existing native configuration rather than a new Flowly switch; no feature ids, selected models or message contents are added to telemetry.

## Acceptance

1. Select a second model and each advertised toggle/select value on an isolated session; native and Flowly state agree and survive plugin reload. The original session id, workspace, dialogue and card status remain unchanged; no prompt is sent.
2. Wrong workspace, archived/deleted task/project/session, non-selectable model, unknown feature, wrong value type, invalid option, overlapping write and provider rejection fail visibly without unauthorized mutation or leaked connection.
3. Reasoning/permission controls remain usable; failed changes refresh actual state; rapid presses cannot overlap other session actions. Desktop and compact menus scroll within their available viewport.
4. Copy/reload preserve message text and ownership; running reload requires confirmation. Native-only capabilities remain reachable through the exact native session entry.
5. Typecheck, focused tests, full-suite results and actual UI/runtime checks are reported separately, including failures/unrun checks. Independent exact-commit verification uses the user-selected codex/gpt-6-luna model in full-access mode.
6. With the menu closed, Fast and Plan On have distinct colored icons. Normal and Plan Off use the neutral icon color. Check both directions and verify that the current option and switch state remain correct after reopening the menu or preview. Cover legacy Fast, Auto-accept, and missing/obsolete select values in the focused regression.

## Unsent attachment drafts (user follow-up 2026-11-17)

Unsent images, generic files and issue/PR references belong to the same session-scoped draft as its text. Leaving the preview, another session, another Flowly surface, or reloading the plugin must restore the same original bytes/metadata and names. Never transfer them to another session. Store original bytes in plugin-owned files on the daemon, with path-free client IDs and typed metadata in composer state; existing version-1 text/queue records remain compatible.

Use scoped add/remove/read RPCs. Add is idempotent by attachment ID; remove names only the selected IDs, preserving concurrent additions. Authorize scope immediately before writes and reads, and preserve invalid/missing data rather than resetting it. composer.read carries metadata/revision only; hydrate bytes for the visible selected session when necessary, with no binary polling. Client cache/pending writes survive component unmount; failed writes retain the local selection and show failure/retry. Disable sending while hydration/save is incomplete. Remove persisted submitted IDs only after acknowledged send/queue success; retain them on failure or uncertain outcome and preserve attachments added during an in-flight send.

Acceptance: image-only and mixed drafts survive Back/reopen, switching sessions, leaving/re-entering Flowly and plugin reload; filenames and bytes are unchanged; removal persists; scope changes refuse; concurrent adds and submitted-ID clearing cannot erase later attachments; no background binary reads; save failure stays visible and recoverable.
